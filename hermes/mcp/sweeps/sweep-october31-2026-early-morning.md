## New: the roster and the pin

[RenewRoster MCP](/hermes/mcp/servers/external/renewroster-mcp/) is a remote Streamable HTTP server at `https://app.renewroster.com/mcp`, confirmed live by a keyless `tools/list` answering **HTTP 401** `invalid or missing API key or OAuth access token`, and it is in the official MCP registry as `com.renewroster/renewroster` at **1.0.0** with a streamable-http remote and a required secret bearer header. It publishes **24 tools**, scoped by the key type chosen at creation. Three of them touch nothing stored, a live RDAP or WHOIS read, a live TLS check and a Certificate Transparency lookup, and the rest is a roster: what expires in the next N days with expired assets included, assets filtered by client and status, bulk import up to a thousand rows, and an update path that covers client, **who pays**, auto-renew, cost and per-asset reminder days.

The commercial fields are the whole reason it earns an entry. A generic expiry monitor already exists in the catalogue, and [WatchCron](/hermes/mcp/servers/external/watchcron-mcp/) watches whether a job stops reporting rather than whether a registration lapses. What this one adds is the question underneath the notification: whose problem is it, what does it cost, has anyone been billed, and `get_report` turns that into the monthly renewal report an agency actually sends. The vendor's containment is a dashboard-only list that keeps billing, plan changes, member invitations, role changes and key creation out of the API entirely. Recorded gap: `tools/list` needs a key, so the tool set and the read and write split are the vendor's publication and not a list this pass measured.

[kosa8 MCP](/hermes/mcp/servers/external/kosa8-mcp/) is a local stdio gateway with a Claude Code plugin, filed on mcp.so the same morning at `03:22:19Z`, verified and featured, with `kosa8.com`, its pricing page, its download page and the plugin repository all **200** and the documentation live at `docs.kosa8.com` at release **v0.11.0**. Its proposition is one machine per tool server: `kosa8 mcp add` takes an image, an egress allow-list and the tool names you permit, and each server then runs as a container in a sandbox named `mcp-NAME` with its own network rule, no view of the other servers and no view of your files. That is a real answer to the way MCP servers are usually launched, which is `npx` moments before they start, as you, with your keys and your network.

The pin is the part that makes this entry rather than a second sandbox guide. Every permission model built for MCP so far watches the tool name, the argument schema or the server identity, and all three stay constant while the thing the model actually reads changes: a tool description is prose, a model follows prose, and a server that edits its description has changed what your assistant will do without touching a field any list can see. kosa8 pins each definition on first use and withholds a later change until a person approves it. Around that sit thirty built-in tools, checkpoint at about **0.7 seconds** with rewind at about one for the whole running machine, fork into live copies, an **egress broker** that injects API keys on the way out so the sandbox holds only a placeholder, approvals requiring one or two named people, and a hash-chained audit log. Recorded gap: nothing was installed or executed, the card's documentation link points at `kosa8.com/docs` which answers **404**, and the MIT licence covers the plugin rather than the signed daemon that runs the VMs.
