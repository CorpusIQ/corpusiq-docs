# Appwrite Skills - Setup Guide

**Source:** [appwrite/skills](https://www.skills.sh/appwrite/skills) via skills.sh - 11.6K combined installs across 11 indexed listings; first seen 2026-11-04 (Nov 4, 2026 evening sweep)
**GitHub:** 29 stars, BSD-3-Clause licence, last pushed 2026-10-20, 11 SKILL.md directories under skills/
**Category:** Appwrite backend development: per-language SDK usage for auth, TablesDB, storage, realtime and functions, plus CLI project and deployment workflows
**Quality Tier:** 🟡 Beta - Snyk Warn on appwrite-cli; BSD-3-Clause; 29 stars.

Appwrite ships eleven skills, one per SDK language plus one for the CLI. They are generated by Appwrite's own SDK Generator against API version 2.5.0 rather than hand-written, so the guidance tracks the SDK surface instead of drifting into a tutorial, and each language skill covers the same ground in its own idiom: client auth with email, OAuth or anonymous sessions, TablesDB queries, file uploads, realtime subscriptions and functions called with API keys.

The CLI skill is the one that is not an SDK wrapper. It covers when to use `appwrite.config.json` against `appwrite client`, pull and push against one-shot service calls, type-safe SDK generation, query flags, CI authentication, regional endpoints and the traps that `--help` does not show.

## Installation

The README installs the collection with the skills CLI, which prompts for skills, agents and project or global scope:

```bash
npx skills add appwrite/skills
```

The same command takes flags when you want no prompts:

```bash
npx skills add appwrite/skills --skill appwrite-typescript --skill appwrite-cli --agent claude-code --global --yes
```

Browse the full list without installing anything:

```bash
npx skills add appwrite/skills --list
```

For Claude Code, Cursor and Codex there is also a plugin per tool that bundles these skills with the hosted Appwrite MCP server. The plugin repositories are linked from the README and are a different install path from the skills CLI, which installs the skill files only.

## Why This Matters for Hermes Agents

SDK churn is the usual failure mode for backend code an agent writes. The model learned an older major version, the snippet nearly compiles, and the error surfaces at runtime against a live project. A per-language skill generated from the current SDK is a cheap way to keep the model inside the supported surface.

The language coverage is unusual. Nine SDKs including Dart and Swift, plus the CLI, is far wider than most agent skill packs, and it means the same backend conventions reach mobile clients rather than stopping at TypeScript and Python.

The CLI skill is the most operational part. Project configuration, pull and push semantics, SDK generation and CI authentication are the steps that break a deployment pipeline, and they are documented as decisions rather than as a command list.

The README also models a good migration habit: a prompt example that moves existing Databases-based code to TablesDB APIs, keeps behaviour identical, and lists every API mapping that changed. That is the shape any mechanical migration should take, in Appwrite or elsewhere.

The caution is maturity. Twenty-nine stars and an auto-generated tree mean the content reflects the generator, not a large body of field reports, so treat the guidance as current API truth and test it against your own project before relying on it.

## Usage

| You say | What happens |
|---|---|
| "build a login flow with Appwrite" | the matching SDK skill writes signup, login, current user and logout against the Account service |
| "query rows where status is active" | the SDK skill uses Query.equal and Query.limit against TablesDB |
| "upload this file and print a preview URL" | the SDK skill calls Storage with the language's native file input |
| "migrate this code from Databases to TablesDB" | the skill maps each API and keeps behaviour identical |
| "deploy a scheduled function" | appwrite-cli pulls the functions, adds the schedule and deploys |
| "set up CI auth for deployments" | appwrite-cli covers CI authentication and regional endpoints |
| "paginate rows in my Flutter app" | appwrite-dart uses cursor queries and exposes them behind a repository |

## Limitations

- Snapshot data, verified 2026-11-04: 11,600 combined installs across 11 indexed listings; 29 GitHub stars; BSD-3-Clause licence; last pushed 2026-10-20. Counts drift over time.
- Snyk warns on `appwrite-cli` in the sampled set. That is the only adverse verdict, and it sits on the skill that touches deployment credentials.

## Pro Tips

- Name the skill in the prompt, for example "use the appwrite-python skill". The README recommends it and it removes the ambiguity when two language skills could match.
- Start new work on TablesDB APIs. The README ships a migration prompt for older Databases code, which is easier to run before a feature grows.
- Keep the endpoint, project ID and API key in environment variables, as every README example does.
- Run `--list` before a global install. Eleven skills written into an agent directory is fine, but knowing which eleven is better.
- Use the CLI skill for deployment work. It documents the config file and CI paths that a general Docker or CI skill will not cover.
